# 와이파이 지킴이 (시제품)

공공 와이파이에서 ARP 스푸핑과 가짜 AP(이블 트윈)를 탐지하고, 방어 명령을 제시하는 도구.
컴퓨터 네트워크 7조 팀 프로젝트. **탐지·방어만 하며 공격 기능은 없다.**

> **처음 받았다면 [docs/SETUP.md](docs/SETUP.md)부터 보세요.** 설치, 데모 실행, 프론트 연결, 문제 해결 순서로 정리돼 있습니다.
> API 규격: [docs/API.md](docs/API.md) · [docs/openapi.json](docs/openapi.json)

## 준비

- Windows 10/11, Python 3.10 이상 (표준 라이브러리만 사용)
- Wireshark 4.x (`tshark`) — pcap 재생 탐지에 필요
- 실시간 캡처까지 하려면 Npcap 추가 설치 (Wireshark 설치 때 Npcap 선택)

## 실행

```powershell
py main.py arp --pcap 캡처.pcap --gateway 192.168.0.1   # pcap 재생으로 ARP 스푸핑 탐지
py main.py arp --iface Wi-Fi --gateway 192.168.0.1      # 실시간 탐지 (Npcap 필요)
py main.py ap                                           # 주변 AP 스캔 → 가짜 AP 탐지
py main.py ap --file scan.txt                           # 저장한 netsh 출력으로 탐지
py main.py learn                                        # 처음 안전하게 접속했을 때: AP와 공유기 MAC 저장
py main.py check                                        # 다시 접속했을 때: 공유기 MAC이 저장한 값과 같은지
py main.py score                                        # 안전 점수 → 대시보드 갱신
py main.py survey --place-type 카페 --place-id C01      # 실태 조사: 주변 AP 공개 정보를 data/survey.csv에 추가
```

결과는 `out/` 에 쌓인다: `events.jsonl`(경고 기록), `results.json`, `dashboard.html`,
`evidence/`(경고 전후 프레임만 잘라 낸 증거 pcap).

방어 명령(정적 ARP 등록, 연결 끊기)은 기본으로 **보여 주기만** 하고, `--defend` 를 붙여야
실제로 실행한다. 정적 ARP 등록은 관리자 권한이 필요하다. 처음 본 MAC이 진짜라는 보장이 없으므로,
공유기 MAC 고정은 `trust.json` 에 저장된 값일 때만 한다 (`learn` 으로 저장, 형식은 `trust.example.json`).

## 서버 + 대시보드 (탐지 엔진 · 백엔드)

팀 설계 구조(Flask + Flask-SocketIO + Scapy + SQLite)를 따른 실행 형태. 위의 `main.py` 명령과 같은 탐지 규칙을 쓰고,
DNS 응답 이상(D1–D3)이 추가돼 있다.

```powershell
py -3.11 -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m guard.diagnose                   # 실행 환경 점검 (Npcap, 권한, 와이파이, 위치 권한)
.venv\Scripts\python run_server.py --no-capture --demo   # 화면 확인: '데모 재생' → ARP·DNS 데모 pcap
.venv\Scripts\python run_server.py --iface Wi-Fi         # 실시간 감시 (Npcap + 관리자 권한)
.venv\Scripts\python run_server.py --replay 캡처.pcap --gateway 192.168.0.1
.venv\Scripts\python run_server.py --iface Wi-Fi --dns-reference 1.1.1.1   # DNS D3 기준 조회 켜기
```

`http://127.0.0.1:5000` 이 대시보드(`frontend/`), `/debug` 가 백엔드 확인 화면이다. 서버는 127.0.0.1에서만 열린다.

- `frontend/` 는 **임시 대시보드**다. 프론트 담당은 `frontend/wifiguard-client.js` 를 가져다 쓰고,
  API·이벤트 형식은 [docs/API.md](docs/API.md) 를 본다.
- 판정은 정상 / 확인 불가 / 주의 / 경고 4단계. 패킷 수집이나 AP 목록 조회가 실패하면 '정상'이 아니라 '확인 불가'로 표시한다.
- 이벤트는 `out/wifiguard.db`(SQLite)에 쌓이고 30일이 지나면 시작할 때 지운다(`--keep-days`).
  권장 대응 명령은 보여 주기만 하고 서버가 실행하지 않는다.
- **지금 유효한 경보**: 같은 대상의 경보는 하나로 묶고, 10분 동안 새 근거가 없으면 빠진다. '확인함'으로 비울 수
  있고, 공격이 계속되면 다시 뜬다. 서버를 다시 켜도 유지된다.
- **보안**: POST는 `X-WifiGuard: 1` 헤더·허용된 출처만, 주소는 127.0.0.1/localhost만 받는다. 내 브라우저에 열린
  다른 사이트가 몰래 '기준값 저장'을 눌러 가짜 공유기를 신뢰하게 만드는 것을 막는다.
- **견고성**: 패킷 하나를 처리하다 오류가 나도 수집은 계속한다 (같은 망에서 이상한 패킷 하나로 탐지를
  멈추게 할 수 없도록). 처음 한 번만 기록에 남긴다.
- 대시보드의 '환경 점검'에서 '확인 불가'의 원인(Npcap 없음, 와이파이 꺼짐, 위치 권한 등)을 볼 수 있다.
- 테스트: `.venv\Scripts\python -m unittest discover tests`

## 탐지 규칙

ARP 스푸핑 — MAC마다 점수를 더해 **40점 이상 '주의', 60점 이상 '경고'**.

| 규칙 | 내용 | 점수 |
|---|---|---|
| R1 | 공유기 IP의 MAC이 바뀜 (일반 기기는 IP 재할당일 수 있어 20점) | 40 |
| R2 | 요청하지 않은 응답, 또는 나에게 직접 온 요청이 10초에 3번 이상 | 30 |
| R3 | MAC 하나가 IP 여러 개를 주장 | 30 |
| R4 | 바뀐 MAC의 제조사(OUI)가 원래와 다름 | 10 |
| R5 | 원래 MAC이 다시 나타나 두 MAC이 번갈아 주장 (arpwatch의 flip flop과 같은 생각) | 30 |

공유기를 교체해도 MAC은 바뀌므로 R1(+R4)만으로는 '주의'에 그친다. '요청한 응답'은
(질의한 IP, 물은 IP) 쌍으로 판단한다 — 남이 공유기 주소를 물은 것은 근거가 되지 않는다.
두 MAC이 한 IP를 다툴 때는 R2·R3 행동을 보인 쪽을 공격자로 추정하고, 근거가 같으면 '확인 필요'로 둔다.

가짜 AP — 같은 이름(SSID)의 AP끼리 비교, 50점 이상이면 경고.

| 규칙 | 내용 | 점수 |
|---|---|---|
| A1 | 같은 이름의 다른 AP는 암호가 있는데 이 AP만 개방형 | 50 |
| A2 | 신뢰 목록에 있는 이름인데 처음 보는 BSSID | 30 |
| A3 | 제조사(OUI)가 다른 AP들과 다름 / 임의 생성 MAC | 20 / 20 |
| A4 | 신뢰 AP보다 신호가 25%p 이상 강함 | 10 |
| 접속 후 | 저장해 둔 공유기 MAC과 지금 공유기 MAC이 다름 (`check`) | 경고 |

DNS 응답 이상 — 내 질문과 돌아온 응답을 짝지어 본다 (UDP 53만). **40점 '주의', 60점 '경고'**.

| 규칙 | 내용 | 점수 |
|---|---|---|
| D1 | 질문 하나에 서로 다른 답이 둘 이상 옴 (질문한 두 서버가 각자 답한 경우, 재전송한 만큼만 답이 온 경우는 제외) | 40 |
| D2 | 질문하지 않은 주소가 응답함 | 30 |
| D3 | 기준 조회 서버의 답과 겹치지 않음. D1·D2가 이미 있을 때만 조회하는 보조 근거, 기본은 끔 | 20 |

## 실태 조사 (F4)

```powershell
py main.py survey --place-type 카페 --place-id C01     # 장소마다 여러 번, 가능하면 서로 다른 날
py eval/analyze_survey.py data/survey.csv              # 통계, 기준값 제안, 공개용 csv, 신뢰 목록
py main.py ap --trust data/trust_survey.json           # 조사 데이터로 만든 신뢰 목록으로 탐지
```

AP가 공개적으로 알리는 정보만 기록한다. 장소는 실제 상호 대신 유형과 팀 코드로 적고,
공개용 `survey_public.csv` 는 BSSID 뒷자리를 가린다. 원본 `data/survey.csv` 는 git에 올리지 않는다.

## 평가

```powershell
py eval/make_scenarios.py 7   # 위협·정상 시나리오 생성 (시드 7) — 파일로만 만들고 전송하지 않음
py eval/evaluate.py           # 재생 평가 → eval/eval_result.json, 화면 출력
py -m unittest discover tests
```

ARP는 같은 pcap을 세 관측 지점에서 평가한다. 와이파이 카드는 목적지 MAC이 자기 것이거나 브로드캐스트인
프레임만 받으므로, 실제 사용 환경은 **피해자 노트북** 지점이다.

2026-10-26 결과 (시드 7, 경고 60점 기준). ARP 공격 8종 × 20개, 정상 100개(3.3시간), 공유기 교체 20개.

| 관측 지점 | 탐지율 (95% CI) | 정상 오탐 | 공유기 교체 경고 | 평균 경고 시간 |
|---|---|---|---|---|
| 전체 관측 | 100% (98–100%) | 0/100 | 0/20 | 3.3초 |
| 피해자 노트북 | 87% (81–91%) | 0/100 | 0/20 | 10.2초 (주의 4.2초) |
| 다른 사용자 노트북 | 12% (8–19%) | 0/100 | 0/20 | 6.0초 |

| 가짜 AP (5종 × 20개, 정상 100개) | 신뢰 목록 없음 | 신뢰 목록 있음 |
|---|---|---|
| 스캔 탐지 | 20% | 77% |
| 접속 후 확인까지 포함한 보호율 | 25% | 100% |
| 정상 오탐 | 0/100 | 0/100 |

시드 11·23에서도 피해자 노트북 탐지율 86.9–87.5%, 오탐 0으로 같았다. 같은 시나리오를 망 전체에서
봤을 때 Wireshark의 중복 IP 표시는 공유기 교체 20/20, 정상 29/100도 표시했다.

DNS (`py eval/dns_eval.py 7`, 결과 `eval/dns_eval_result.json`). 정상 세션 4종 × 100개, 위협 4종 × 20개.
세션 하나는 노트북이 30–60개 도메인을 조회한 기록이고, 위협은 그 중간에 의심 응답 한 번을 끼워 넣었다.
시드 11·23도 결과가 같다 (규칙이 결정적이어서 타이밍만 다른 합성 데이터로는 차이가 나지 않는다).

| 세션 | 기준 조회 없음 (주의 이상 / 경고) | 기준 조회 있음 |
|---|---|---|
| 정상: 일반 · 서버 2개로 재질문 · 재전송 · 재전송에 다른 답 | 0 / 0 (각 100개) | 0 / 0 |
| 같은 망 다른 기기가 먼저 답 + 진짜 답 (D2+D1) | 20 / 20 | 20 / 20 |
| 서버 주소로 위장한 답이 먼저 + 진짜 답 (D1) | 20 / 0 | 20 / 20 |
| 같은 망 다른 기기의 답만 (D2) | 0 / 0 | 20 / 0 |
| 서버 주소로 위장한 답만, 진짜 답은 안 보임 (중간자) | 0 / 0 | 0 / 0 |

평가 중 '재전송에 다른 답'(라운드로빈)이 100% '주의'로 오탐되는 것을 찾아, 서버별 질문 수보다 답이 많을 때만
D1로 세도록 고쳤다. 중간자 위치에서 진짜 답을 가로채고 위장한 답 하나만 주면 DNS 모듈로는 볼 수 없다.
이 경우 중간자가 되는 과정(ARP 스푸핑)을 ARP 모듈이 잡아야 한다.

알려진 한계
- 공유기 쪽만 오염하는 공격은 피해자 노트북에 아무 프레임도 오지 않아 볼 수 없다 (피해자 지점에서 놓친 21개 중 20개).
- 느린 공격(15초 간격)과 캡처 전부터 진행 중인 공격은 진짜 공유기가 다시 응답해야 '경고'가 된다 (평균 23–25초). '주의'는 대부분 즉시 뜬다.
- 신뢰 목록이 없는 곳에서는 개방형 가짜 AP만 막는다. 접속 후 확인은 가짜 AP가 자기 공유기를 쓴다는 가정에 기댄다.
- DNS는 UDP 53만 본다. 브라우저·Windows의 보안 DNS(DoH)를 쓰면 질문이 보이지 않는다. 실시간 수집 중
  2분 동안 DNS가 안 보이면 DNS 모듈을 '확인 불가'로 바꿔 알린다. 실험할 때는 보안 DNS를 끈다.
- 재전송된 질문에 위장한 답을 끼워 넣으면 D1 예외(재전송)에 걸려 놓칠 수 있다.
- 시나리오는 직접 만든 합성 데이터다. 실험망 실측과 실시간 캡처(Npcap)는 아직 하지 않았다.
